# Contributing

`mise install && pnpm install`, then `pnpm lint` (Biome, and `checks/comments.mts`), `pnpm test` and `pnpm validate`. CI runs all three; the last two need the `claude` CLI. `pnpm typecheck` needs the typings a logged-in Claude Code session writes to `.claude-plugin/types/`.

- Codex, OpenCode and agy run over [ACP](https://agentclientprotocol.com) (Agent Client Protocol, a standard way to drive coding agents) through `relay/relay.mjs`, a committed bundle. Run `pnpm build:relay` after changing `relay/src/` or the SDK version; CI fails when the bundle doesn't match.
- `VIA_TRACE=1` in Claude Code's environment makes each run behind the relay write a trace: the prompt, every line the relay printed and each inbox line, with times, in `~/.claude/via/traces/<agent>-<time>.jsonl`. For development; pi, which runs without the relay, writes none. A trace holds everything the agent read, ran and printed, and every message and answer you sent it, so it may hold secrets: it is readable only by you, and nothing deletes it.
- `relay/codex-acp/` is the lockfile `codex-acp` installs from (`npm ci --ignore-scripts`); `hooks/install.ts` does the install.
- `hooks/acp/` is the generic ACP client; `pnpm lint` fails if it imports anything of `via`'s.
- Each Claude Code permission mode means the same for every harness, in its nearest terms: never more than the person gave Claude, and no less unless the harness has nothing closer. An ACP harness's mode table (`AcpModes`, `hooks/acp/spec.ts`) must name every mode, so a new one is a type error until each harness maps it; each harness's tests pin its rows.
- `hooks/record.ts` keeps one record per agent in `$.store`, so an agent continued in a new process still has its session, mode and last answer. `hooks/agents.ts` serves the `agents` tool (`$.tool.register`) from those records: list, open (an adapter's `reopen`) and forget (an adapter's `forget`, a run of the relay's `RELAY_DELETE`, after `$.ui.ask`).
- `hooks/writer.ts` writes a run's steps, for `via` agents and their nested ones.
- Harness tool calls reach Claude Code as calls to the MCP tool `step`, which runs nothing: `via` answers each with what the harness reported, and refuses a `step` call it didn't make.
- A harness's question to the person (ACP elicitation) is a `step` call too. `hooks/questions.ts` maps its form onto Claude Code's AskUserQuestion dialog, which `via` opens with `$.ui.ask`; its own `tool.call` hook on that AskUserQuestion call shows all the questions and keeps the whole result, as `$.ui.ask` returns only a label and `$.tool.call` refuses AskUserQuestion. A form that doesn't map (a link to open, more than four fields, a choice of more than three, another field type) goes through to the step server (`mcp/step.mts`), which asks it as an MCP elicitation in Claude Code's own form. Either way the reply goes back to the harness through the inbox.
- "Let Claude answer", the person's `askUserQuestionTimeout` passing, or a `-p` run hands the question to the main agent: the step after the question call is a `SendMessage` to `main` from the `via` agent, and the main agent's `SendMessage` back is the answer, read onto the form, while the question is open (`handed` in `hooks/acp/steps.ts`). Claude Code's own idle timer leaves a plugin's dialog alone, so `via` times it from the setting. Only a background agent offers this: a foreground agent's message reaches the main agent only after its turn ends (seen live on 2.1.331), while the harness would wait on the answer.
- A collapsed group of only `step` calls is one counted line from its first call (`hooks/register.ts`, `drawGroup` in `hooks/acp/render.ts`), failed and interrupted calls counted on it, so a group doesn't change height as calls join, end or fail. ctrl+o shows each call. A group of mixed calls keeps Claude Code's drawing, as does one that shows other rows (hook timings, recalled memories) with no failed call, from then on. A row that joins a group via draws, with or after a failed call, is hidden, as the props can't tell the two apart (`tests/group-rules.test.ts`).
- Nested agents need the harness to report subagents over ACP ([subagents RFD](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/rfds/subagents.mdx)); `codex-acp` does.
- A nested agent's task is its Agent call's prompt, and a later message to it while it works is a row in its view, both from the RFD's `session_message`; a message to the `via` agent itself is a row in its own view. A message is said once its session moves on (another update of it) or the prompt ends, so its later upserts and chunks count, and a sender's view waits until it names its recipient. A nested agent shows once it has its task, or once it works, so a title or role announced after its task is not shown. `codex-acp` sends these messages for Codex's v1 subagent tools. The model picks the version, whatever `multi_agent` says, and the v2 tools send no text (openai/codex#61750): gpt-6-luna on codex-cli 0.169.0 picked v2, so its nested agent got its title.
- `pnpm test:relay` tests the relay against a fake agent; against testy, ACP's reference agent (`relay/test/testy.test.mts`; `cargo build --manifest-path ci/testy/Cargo.toml --target-dir ~/.cache/via/testy`, outside the plugin's folder, as `claude plugin eval` refuses Cargo's hard links); and the real codex-acp and `opencode acp` against a fake model (`relay/test/real-*.test.mts`). The testy and harness tests skip when their binary isn't there, and all run in CI's `harnesses` job. `relay/checks/` holds the live checks, which spend tokens and run on your own login: `pnpm check:relay <workdir> <model> <bad-model> -- <agent command...>` (stream, interrupt, resume, stop, a refused model and steer; set `RELAY_STEER` as the harness's adapter does) and `pnpm check:relay-ask <workdir> <agent mode> <allow|deny> <prompt> -- <agent command...>` (answers the relay's permission questions as `via` does).

## Tests

- TypeScript, type-checked with the code (CI too); fixtures typed against the ACP SDK.
- A test waits on the event it needs: a model request, a line the relay prints, a notification, a file the command under test writes in one step. Never on time. Each wait fails when the process it waits on ends. The only timers are backstops that end a hung run: `relay/test/support/backstop.mts`, a spawned process's `timeout`, a test's `timeout`.
- A test checks behaviour where it crosses a boundary: what the relay prints, what a harness or model receives, what Claude reads. Not internal shapes.
- A new test fails without the change it covers. Show it before committing.
- No tokens and nothing of yours: the fake agent, the fake model and an empty HOME, no network beyond localhost. What only a real model can show goes in an eval (`evals/`, `pnpm eval`), with a cost cap.
- A version a test depends on lives where Dependabot bumps it.
- The first two hold by construction and by lint: the test runners pick up only TypeScript test files (`*.test.ts(x)`, `relay/test/**/*.test.mts`, `mcp/test/*.test.mts`), and Biome's test override in `biome.json` refuses a timer, `global`, `globalThis` and `AbortSignal` in a test, and a test importing a JavaScript file of ours.

## Comments

None in code (`checks/comments.mts` fails on any). A rule goes in a test, a type or a name; why a change was made, and what was tested live, goes in its commit message. Only directives stay: a lint rule's `biome-ignore` with its reason, and a bare `@ts-expect-error`. A comment that seems needed is a missing test or a better name.

## Commits

- A commit that leaves known work undone opens an issue for it, and its message names the issue. A gap noted only in a commit message is forgotten: #41 noted that `answerCall` still waited without a bound, and three weeks later a Codex step was refused for it.
